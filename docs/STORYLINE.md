# Page-by-Page Storyline

## The narrative in one sentence

GitHub Copilot expands what an engineer can do; CopilotWith turns that individual capability into an evidence-led, human-governed modernisation programme that can move safely from one application to an entire estate.

## The dramatic arc

The experience is not a catalogue of features. It makes one cumulative argument in three acts:

1. **Possibility:** GitHub Copilot can participate across the engineering lifecycle, not only generate code.
2. **Control:** CopilotWith adds specialist methods, evidence, handoffs, and human accountability so that capability can be trusted in consequential modernisation work.
3. **Proof and scale:** The operating model can understand an application, form a plan, implement a bounded change, prove it, and repeat the pattern across a portfolio.

Every page should move the audience from one belief to the next. A presenter should not explain every visual element. Use the interaction to reveal the answer to the page's central question.

## Page 0: GitHub Copilot — Art of Possibility

**Central question:** What becomes possible when Copilot participates across the whole engineering lifecycle?

**What this page is trying to say**

GitHub Copilot is broader than code completion. It can help an engineer understand an unfamiliar system, plan work, implement changes, create tests, investigate security concerns, prepare delivery assets, and reason about operational signals. The centre of the visual is engineering intelligence; the surrounding capabilities show that the value appears throughout the flow of work.

The phrase **Human Directed** is essential. The page is not promising autonomous software delivery. It establishes a partnership: Copilot increases the engineer's reach and speed, while the person supplies intent, context, judgment, and accountability.

**Audience belief before the page**

“Copilot is mainly a coding assistant.”

**Audience belief after the page**

“Copilot can amplify an engineer across the lifecycle, but broader organisational use needs a way to direct and govern that power.”

**How to tell the story**

Start at the centre, not at the individual capability nodes. Say that Copilot brings an engineering reasoning layer into the tools teams already use. Then travel around the lifecycle:

- **Understand:** reduce the cost of entering an unfamiliar codebase.
- **Plan:** convert goals, constraints, and findings into reviewable work.
- **Code:** implement a bounded change in the actual repository context.
- **Test:** create safety nets and compare behaviour before and after change.
- **Secure:** identify dependency and code risks without claiming to accept them.
- **Deliver:** prepare infrastructure, pipelines, and deployment assets.
- **Operate:** connect runtime evidence back to engineering decisions.

End on the bridge at the bottom. Individual acceleration is the possibility; CopilotWith is the programme; people retain accountability.

**Interaction cue**

Use **Explore Demos** when the audience wants immediate examples. Use **Introduce CopilotWith** for the intended narrative sequence.

**Do not imply**

- Copilot independently owns technical direction.
- Every capability is fully autonomous.
- Generated output is correct merely because it was generated.
- Human review is an administrative step rather than a decision.

**Transition**

“If this is what one engineer can do with Copilot, the next question is how an organisation applies it repeatedly, safely, and consistently across a modernisation estate.”

## Page 1: CopilotWith Mission — One Control Room, Many Estates

**Central question:** How does the broad possibility become a repeatable modernisation mission?

**What this page is trying to say**

Modernisation is not one technology problem. An estate may contain .NET Framework, COBOL, Progress, Uniface, Liferay, middleware, analytics platforms, and delivery pipelines. Each has different evidence, failure modes, transformation mechanics, and proof standards.

CopilotWith is introduced here as the programme wrapper around GitHub Copilot. GitHub Copilot supplies analysis and engineering capability. CopilotWith supplies specialist routes, an evidence chain, explicit gates, and a shared mission structure. Azure is shown as a possible target and operating environment, not as a predetermined answer for every workload.

The launch bay communicates breadth without claiming that every pack has identical maturity. Its job is to make the audience see an estate rather than a single repository.

**Audience belief before the page**

“We can use one powerful prompt or one general agent for every application.”

**Audience belief after the page**

“Different estates require different specialist methods, but they can still operate inside one governed programme.”

**How to tell the story**

Let the application selector move through several technologies. Point out that the active pack changes with the application type. The sequence along the page — discover, design, secure, modernise, validate, deploy — is the common mission spine. The method within each step changes by technology.

The three-part promise strip defines responsibilities:

- **GitHub Copilot:** engineering analysis, planning, transformation, and testing.
- **CopilotWith:** specialists, governance, evidence, and programme scale.
- **Azure:** target architecture, deployment, and operations where appropriate.

**Interaction cue**

Select contrasting estates such as COBOL, middleware, and HDInsight. The contrast makes specialist routing tangible. Then start the mission.

**Do not imply**

- Every source platform should move to the same target.
- Azure selection removes the need for architecture decisions.
- The displayed breadth means every pack has production evidence at the same maturity.

**Transition**

“A shared mission is useful only if it prevents speed from outrunning understanding. That is why the programme begins with evidence.”

## Page 2: Operating Model — Evidence Before Execution

**Central question:** What makes this controlled engineering rather than AI-generated activity?

**What this page is trying to say**

CopilotWith separates modernisation into two equally important layers:

1. **Estate Intelligence:** discover, classify, connect, and prioritise what exists.
2. **Governed Execution:** protect behaviour, design the change, implement it, and prove the result.

The evidence reactor sits between them because execution should not start from unclassified assumptions. Findings are marked as **Observed**, **Inferred**, **Assumed**, or **SME-Confirmed**. The labels stop plausible language from becoming false certainty.

The human gate is not placed only at the end. People own priorities, target direction, architecture, risk, exceptions, and acceptance throughout the loop. Agents create evidence, options, tests, and bounded changes. This division of accountability is the foundation of the whole programme.

**Audience belief before the page**

“Governance means reviewing AI output after the work has already happened.”

**Audience belief after the page**

“Governance shapes what agents may do, what evidence they must produce, and where a person must decide before work progresses.”

**How to tell the story**

Read the page from left to right. On the left, the programme earns the right to propose change by understanding the estate. In the centre, evidence is classified and validated. On the right, approved work becomes small, reviewable engineering increments.

Use the accountability rail to make the operating contract explicit. The strongest line on this page is not about an AI capability; it is the **Never Autonomous** boundary: no self-merging, no production push, no risk acceptance, and no invented facts.

**Interaction cue**

Pause here. This page carries the governance thesis and should not be rushed by autoplay during a customer conversation.

**Do not imply**

- “Inferred” means weak or unusable; it means reasoned and not directly observed.
- SME confirmation replaces technical evidence.
- A human gate makes weak evidence acceptable.

**Transition**

“The operating model is common, but the method cannot be generic. The evidence now determines which specialist pack should take ownership.”

## Page 3: Specialist Pack Atlas — The Evidence Chooses the Route

**Central question:** How does CopilotWith avoid applying a generic method to specialised systems?

**What this page is trying to say**

A pack is more than a prompt. It packages specialist roles, skills, evidence requirements, workflow order, expected outputs, and non-negotiable guardrails for a problem domain. The atlas makes those differences inspectable.

The page also communicates maturity honestly. **Proven in engagement**, **demonstrated**, **calibrated**, and **designed capability** are not marketing synonyms. They indicate different levels of supporting evidence. A designed pack may have a coherent method and worked sample while still requiring validation in the customer's context.

**Audience belief before the page**

“Specialisation is mainly different agent names placed over the same workflow.”

**Audience belief after the page**

“Each route changes what evidence is read, what method is followed, what outputs are expected, and what boundary cannot be crossed.”

**How to tell the story**

Choose packs that expose materially different analysis problems:

- **COBOL:** executable code, copybooks, JCL, CICS, VSAM, and DB2 require paragraph-level and data-flow reconstruction.
- **Progress:** the resolved compile view matters because includes, preprocessing, and runtime paths can change behaviour.
- **Middleware:** contracts, transformations, runtime flows, and cutover evidence dominate.
- **Reverse Engineering:** unknowns must remain visible when source is incomplete.
- **Data Estate:** discovery is read-only and must pass a governance gate before design.

For each selection, follow the dossier in the same order: evidence inputs, intelligence method, execution method, outputs, maturity, guardrail.

**Interaction cue**

Ask the audience to name a difficult estate in their environment, then choose the nearest pack. Use the changed dossier to show that routing is substantive.

**Do not imply**

- A designed capability is proven delivery experience.
- Selecting a pack eliminates discovery.
- Agent count is a measure of quality.

**Transition**

“We now have the operating model and specialist routes. The demo studio shows how that logic changes for three very different application stories.”

## Separate Destination: Demo Studio

**Central question:** What does the model look like when applied to recognisable application scenarios?

**What this destination is trying to say**

The Demo Studio is deliberately separate from the linear programme. It is a library of examples, not a mandatory governance stage. The persistent **Demos** control lets a presenter enter it whenever the audience needs proof, then return to the programme argument.

Every demo uses the same three-part frame:

- **Before:** what is observed or documented about the current state.
- **Modernisation Plan:** what is proposed, sequenced, and subject to human approval.
- **After:** the intended outcome, which is accepted only when test and deployment evidence support it.

This shared frame makes the examples comparable without pretending that they are the same migration.

### Demo 1: eShop — Modern .NET and Aspire

#### Before: A modern distributed application

**Question answered:** What can CopilotWith do when the application is already modern?

This page prevents a common false narrative: not every modernisation engagement starts with obsolete technology. `dotnet/eShop` is a modern .NET 10 and Aspire reference application. The challenge is understanding distributed topology, protecting service contracts, improving operational readiness, and making delivery repeatable.

The audience should leave believing that modernisation includes continuous architecture and delivery improvement, not only framework upgrades.

**Presenter line:** “There is no invented legacy here. The current state is already modern; our job is to understand it and industrialise its delivery safely.”

#### Modernisation Plan: Industrialise the delivery path

**Question answered:** What work remains when the runtime and architecture are current?

The plan focuses on service contracts, critical journeys, identity, secrets, observability, and repeatable cloud delivery. This demonstrates that CopilotWith responds to actual evidence rather than forcing every application through a version-upgrade template.

The plan is explicitly proposed. Architects and maintainers must decide which boundaries are stable, which operational standards apply, and which deployment target is appropriate.

**Presenter line:** “The plan is not ‘upgrade .NET.’ It is to make an already-modern system easier to understand, verify, operate, and release.”

#### After: A reviewable Azure-ready path

**Question answered:** What counts as improvement for an already-modern application?

The target outcome is not a new architecture diagram for its own sake. It is verified service behaviour, reviewed delivery assets, surfaced operational controls, and a human-approved release path. The word **ready** matters: the page does not claim that a deployment occurred.

**Presenter line:** “The outcome is confidence and repeatability, backed by evidence, without rewriting a system merely to create activity.”

### Deep Replay: eShopOnWeb

The preserved eShopOnWeb section provides a more detailed repository-oriented replay. It is related to the eShop story but is a distinct ASP.NET Core 8 reference application.

- **Understand:** reconstruct the deployable surfaces, domain core, infrastructure boundary, and Blazor admin boundary.
- **Protect:** map four test projects to domain rules, web journeys, and API contracts.
- **Deliver:** connect Dockerfiles, Docker Compose, `azure.yaml`, Bicep, App Service, SQL, and Key Vault assets into a reviewable delivery path.

The repository structure is source-grounded. Timed agent events are simulated. This section demonstrates how evidence moves through specialist missions; it does not claim a live scan.

### Demo 2: Contoso University — Legacy .NET Framework

#### Before: Windows-bound university application

**Question answered:** Why is this application not ready for a simple lift and shift?

The current state surfaces .NET Framework 4.8, ASP.NET and Windows hosting assumptions, plus a legacy dependency surface. The point is not that “legacy is bad.” The point is that hidden platform coupling affects sequencing, target choice, test strategy, and risk.

**Presenter line:** “Before proposing a target, we need to know which behaviours and dependencies are tied to the current runtime and host.”

#### Modernisation Plan: Move in protected increments

**Question answered:** How do we reduce migration risk without freezing progress?

The sequence begins with characterisation tests, then works through the dependency graph and hosting model while keeping architecture decisions gated. The plan promotes incremental migration because each step can be reviewed, tested, and reversed more easily than a big-bang rewrite.

**Presenter line:** “We are not asking an agent to rewrite the application. We are asking the programme to create the smallest defensible sequence of changes.”

#### After: Modern .NET with proof

**Question answered:** When can the programme honestly call the migration successful?

A modern runtime alone is insufficient. Success includes portable hosting, automated parity checks, reviewable pull requests, and explicit residual risk. The target is accepted by people after evidence passes, not declared complete by the implementation agent.

**Presenter line:** “The after state is code plus proof plus an approval record.”

### Demo 3: Spring PetClinic — PostgreSQL and AKS

#### Before: Spring application with migration debt

**Question answered:** What must be understood before moving a Java application to Kubernetes?

The current state highlights the Spring application, PostgreSQL persistence, credential-based connectivity, dependencies, and local runtime assumptions. Kubernetes is not presented as the first action. Assessment comes first because containerising an insecure or poorly understood application only moves its problems.

**Presenter line:** “The cluster is a destination, not the modernisation method. We begin with application and dependency evidence.”

#### Modernisation Plan: Secure, containerise, then deploy

**Question answered:** What is the safe dependency order for this migration?

The sequence is intentional: remediate vulnerable dependencies, design managed identity and passwordless database access, build and scan the container, then validate AKS manifests, probes, and deployment assumptions. Later steps depend on evidence from earlier ones.

The page demonstrates that security and identity are architecture work, not post-deployment checks.

**Presenter line:** “Passwordless access, container security, workload identity, and health probes are part of the migration design, not a hardening sprint after launch.”

#### After: Passwordless PostgreSQL on AKS

**Question answered:** What makes the target state operationally credible?

The outcome combines passwordless PostgreSQL, AKS workload identity, health and readiness probes, and deployment validation. No single item is enough. The target becomes credible when identity, workload packaging, runtime health, and verification work together.

**Presenter line:** “The after state is not ‘it runs in AKS.’ It is an identity-aware, observable workload with evidence that it can be operated.”

**Demo Studio transition back to the programme**

“Those examples differ in technology and intent, but the governing pattern is stable: understand the current state, approve a plan, implement bounded work, and demand evidence for the outcome.”

## Page 4: Application X-Ray — Turn Source into an Explainable System

**Central question:** How does the programme understand an unfamiliar legacy application well enough to plan change?

**What this page is trying to say**

Source files alone are not an architecture explanation. The X-Ray converts repository evidence into a topology of runtime, messaging, storage, and hosting dependencies. Each blocker stays connected to its evidence, affected components, risk, proposed target pattern, and accountable specialist.

The scan animation communicates progressive discovery, not magical omniscience. The prompt controls show that an engineer can interrogate the model from different angles, such as containerisation or messaging risk.

**Audience belief before the page**

“AI assessment produces a report full of findings.”

**Audience belief after the page**

“A useful assessment creates an explainable dependency model that supports specific decisions.”

**How to tell the story**

Let the scan expose the four blocker families. Select MSMQ and explain the distinction between an observed dependency and the proposed Azure Service Bus target. Ask what prevents containerisation to show that several constraints combine into one delivery risk.

The page uses an illustrative Contoso University payload. Counts, topology, and timing are replay constructs, not measured customer results.

**Interaction cue**

Select individual nodes, then ask the containerisation question. This moves the audience from isolated findings to cross-cutting reasoning.

**Transition**

“Once the system is explainable, no single generalist should own every conclusion. The next page shows specialist responsibility and handoff.”

## Page 5: Agent Team — A Virtual Engineering Organisation

**Central question:** Who does the work, and how is responsibility controlled?

**What this page is trying to say**

CopilotWith is not one chatbot wearing different labels. Specialist agents have bounded missions, tools, outputs, and approval constraints. Work moves through a chain: documentation, dependency analysis, architecture, strategy, implementation, testing, security, UI, and deployment.

The handoff theatre is the core of the page. It distinguishes facts from recommendations and readiness from decisions:

- **Observed:** evidence found in the system.
- **Proposed:** a recommendation requiring evaluation.
- **Ready:** an artefact prepared for review.
- **Decision:** a point owned by a person.

The larger inventory indicates reusable organisational capability. It should not be presented as 127 agents operating simultaneously or autonomously.

**Audience belief before the page**

“Multi-agent means several bots collaborating without supervision.”

**Audience belief after the page**

“Multi-agent delivery is useful when ownership is specialised, handoffs are explicit, and authority remains bounded.”

**Interaction cue**

Select several agents and compare powers, tools, output, and approval boundary. Replay the handoff and stop on Human Reviewer.

**Transition**

“The specialists can produce options and evidence. They cannot decide the programme's priorities or accept its risk. That is the purpose of the next page.”

## Page 6: Modernisation Plan — Constraints Become Decisions

**Central question:** How does the plan adapt to business priorities without surrendering architectural control?

**What this page is trying to say**

There is no universally correct modernisation plan. “Fastest migration,” “lowest risk,” “cloud-native,” and “minimal code change” produce different sequences and trade-offs. Constraints such as zero downtime, unchanged database, hybrid operation, or no public endpoints materially affect the plan.

The generated tasks are not an autonomous commitment. They are a transparent proposal with effort, risk, dependencies, specialist ownership, and an explicit decision gate. Autoplay stops here because moving from understanding to change is consequential.

**Audience belief before the page**

“The AI will determine the best migration plan.”

**Audience belief after the page**

“The programme can reason about options, but people must choose which trade-offs serve the organisation.”

**Interaction cue**

Change from lowest risk to fastest migration and add zero downtime. Let the audience see the plan react. Return to the preferred scenario, explain why, and then approve it.

**Do not imply**

- The displayed effort is a customer estimate.
- Approval validates facts that have not been evidenced.
- A selected priority overrides security or policy controls.

**Transition**

“Approval does not unleash a rewrite. It authorises one bounded, reviewable slice.”

## Page 7: Transform — Make One Controlled Change

**Central question:** What does agent-assisted implementation look like when the scope is constrained?

**What this page is trying to say**

The unit of progress is a bounded code change. The illustrative transformation replaces an MSMQ publisher with Azure Service Bus and shows the associated configuration, tests, security considerations, container assets, and build feedback.

The split editor makes the change legible. The side panel connects implementation to the approved task and shows that the agent is allowed to edit and repair within scope, but not to redesign the programme or merge its own work.

**Audience belief before the page**

“Agentic modernisation means asking AI to convert the whole application.”

**Audience belief after the page**

“Agentic implementation is most credible when each change is small enough to inspect, test, and reverse.”

**Interaction cue**

Run **Modernise this component**. Walk through the diff from contract and configuration to tests and delivery assets. Avoid focusing only on lines generated.

**Evidence boundary**

The Contoso code, build output, and transformation result are illustrative replay content. They demonstrate the contract of a connected implementation, not a measured migration run.

**Transition**

“Code generation is not the finish line. The change now moves to independent proof.”

## Page 8: Proof — Security, Test, and Independent Review

**Central question:** How does the programme know that a change is safe enough to present for acceptance?

**What this page is trying to say**

Claims must resolve to evidence. Build, unit tests, compatibility tests, security checks, container validation, and pull-request preparation form a proof chain. The maker does not become the checker merely because it can run tools.

The page separates three responsibilities:

- Implementation produces a candidate change.
- Independent gates test technical claims and surface exceptions.
- A human decides whether the evidence is sufficient for progression.

The evidence drawer reinforces provenance across the entire experience. It should be opened here to show which records are observed, simulated, pending, or controlled.

**Audience belief before the page**

“If the generated code compiles, the task is complete.”

**Audience belief after the page**

“A change is ready for human consideration only when independent evidence supports its behavioural, security, and delivery claims.”

**Interaction cue**

Run validation, inspect each check, open the evidence drawer, and point out that the pull request is prepared but not merged.

**Transition**

“One proven slice creates progress. A modernisation programme must also explain how many slices accumulate into a credible transition state.”

## Page 9: Before / After — The Modernisation Time Machine

**Central question:** How does the architecture evolve without a fictional big-bang cutover?

**What this page is trying to say**

The slider presents modernisation as a sequence of transition states. Runtime, messaging, storage, hosting, and delivery practices do not all change at once. Each future-state node represents accumulated approved slices with tests and operational evidence.

The middle of the slider is the most important position. It acknowledges hybrid architecture, temporary adapters, parallel operation, and controlled migration debt. These states are not failure; they are often the safest route between two operating models.

**Audience belief before the page**

“A transformation is best communicated as a clean before-and-after architecture diagram.”

**Audience belief after the page**

“A credible plan makes intermediate states explicit and governs them until they can be retired.”

**Interaction cue**

Drag slowly and stop around the midpoint. Ask which temporary states the customer's organisation can operate safely and which require additional controls.

**Transition**

“If this pattern can govern one application's transition, the final question is how to repeat it across an estate without losing evidence or control.”

## Page 10: Portfolio — From One Mission to an Operating Model

**Central question:** How does individual engineering acceleration become enterprise modernisation capacity?

**What this page is trying to say**

Portfolio scale comes from standardising evidence, methods, specialist roles, decision gates, and proof — not from running more autonomous agents. The estate map turns application findings into waves based on risk, value, dependency, and readiness.

The adoption ladder deliberately starts below multi-agent delivery:

1. **Assisted analysis:** one engineer uses Copilot on one system.
2. **Skill-driven workflow:** reusable methods, evidence templates, and gates.
3. **Specialist agents:** bounded roles own recurring tasks.
4. **Multi-agent delivery:** maker, checker, and governance roles coordinate.
5. **Portfolio operating model:** standards and evidence govern the estate.

Level 2 is the recommended starting point for many organisations because repeatable methods and controls should precede greater autonomy.

**Audience belief before the page**

“Scaling means deploying more agents across more repositories.”

**Audience belief after the page**

“Scaling means making quality, evidence, and accountability repeatable across applications, teams, and waves.”

**Interaction cue**

Generate the waves, switch among personas, and walk through adoption levels. For executives, emphasise prioritisation and risk. For architects, emphasise patterns and transition states. For developers, emphasise reusable workflows and bounded tasks.

**Closing message**

“GitHub Copilot gives engineers greater capability. CopilotWith gives the organisation a governed way to apply that capability repeatedly. The next step is not to automate the whole estate. It is to choose one application, one consequential decision gate, and one proof standard for a connected mission.”

## Persistent Controls and Their Narrative Role

### Demos

This is a deliberate side door into proof. It lets a presenter answer “show me” without abandoning the programme story. Entering the studio pauses autoplay because demos should be explored intentionally.

### Show Me the Evidence

This control is always available because evidence is not a final appendix. It is a cross-cutting property of every claim in the experience.

### Persona Switch

Executive, Architect, and Developer views demonstrate that the underlying evidence remains stable while emphasis changes for the audience. Persona must never alter the facts themselves.

### Autoplay

Autoplay establishes momentum through the non-consequential discovery act. It stops before plan approval to make the human boundary visible. A presenter should treat that stop as part of the story, not an interruption.

## Claim Discipline for the Whole Experience

Use these terms consistently:

- **Source-grounded:** supported by the named repository, document, or lab.
- **Observed:** directly present in supplied evidence.
- **Inferred:** reasoned from evidence but not directly stated.
- **Assumed:** intentionally unverified and requiring confirmation.
- **Proposed:** a possible plan or target requiring a decision.
- **Simulated / deterministic replay:** pre-authored activity used to demonstrate the future connected experience.
- **SME-confirmed:** reviewed and validated by an accountable person.

Never describe the current experience as a live customer scan. Never merge facts from eShop, eShopOnWeb, Contoso University, and PetClinic into a single application journey. Never present target-state language as proof that deployment or migration has occurred.
